# README Portfolio

ポートフォリオ・対外公開向けの README を、実コードと突き合わせて精度高く仕上げるスキル。複数プロジェクトでの README 整備を通じて固めた定型プロセスを再現する。

## 起動条件

- 「READMEを書き直して」「ポートフォリオ向けにREADMEを」「対外公開READMEを作る」「プロジェクトのREADMEを更新」等のトリガー
- 既存 README が薄い・古い・内部向けで対外公開に耐えないとき
- 受託案件の根拠資料、転職活動のポートフォリオ、GitHub 公開の準備が必要なとき

## 大原則

1. **既存ドキュメントの記述を継承するだけで書かない** — `CLAUDE.md` / `docs/system-architecture.md` / 各サブシステム README は素材であり、それらの中の記述が古い・誤っている可能性を常に疑う。**必ず実コードと突き合わせる**
2. **数値はすべて実測** — コード行数、自動更新間隔、TTL、バージョン、カテゴリ数などは記憶や既存ドキュメントから取らず、`wc -l` / `grep` / `Read` で実コードから取る
3. **段階的に作る、一発で完成させない** — 初版（粒度A: 概要レベル） → 実コード検証 → 1段階詳細化（粒度B） → 完璧化、の最低3段階を踏む
4. **submodule / untracked / リンク切れを書く前に把握する** — 「リポジトリ構成」を書き始める前に、`git ls-files` / `git submodule status` / .gitignore で実態を確認する
5. **既存の図・シーケンス図・アーキテクチャ図も鵜呑みにしない** — embed する前に、それらの中の記述も実コードと突き合わせる
6. **ユーザーが「正しいか？」と問い直したら立ち止まる** — 自信のあるまま push してから訂正コミットを積むのではなく、検証を先に走らせる

## 実行フロー

### Step 1: 起動時スキャン

書き始める前に、リポジトリの実態を把握する。並列で取得:

```bash
ls -F                          # ルート直下の全ファイル/ディレクトリ
cat .gitignore                 # 何が ignore されているか
cat .gitmodules 2>&1           # submodule の有無
git ls-files | head -50        # 追跡対象の概観
git submodule status 2>&1      # submodule の HEAD
git status -s                  # untracked の量
ls docs/sequence-diagrams/ 2>&1  # 既存シーケンス図の有無
```

`README.md` が既にある場合は読む。`CLAUDE.md` / `docs/01-overview.md` / `docs/system-architecture.md` も読む。各サブシステム README をリストアップ。

### Step 1.5: シーケンス図整備状況の確認（連鎖トリガー）

Step 1 のスキャンで以下のいずれかに該当した場合、`AskUserQuestion` で先行整備を提案:

- `docs/sequence-diagrams/` が存在しない
- 存在するが個別図が不足している（例: 主要ロールに対応する図が欠けている）
- 存在するが古く、対象コードベースと乖離している可能性がある

提示形式:

> 「機能別シーケンス図が整備されていません（または不足しています）。先に `/mermaid-sequence-diagram` を実行してから本スキルに戻る方が、README の完成度が一段階上がります（実装根拠付きの俯瞰図を本文に embed できる）。どうしますか？」

選択肢:
- 「先に `/mermaid-sequence-diagram` を実行する（推奨）」 — `Skill` tool で起動。完了したら本スキルの Step 2 に戻る。`/mermaid-sequence-diagram` の Step 8 から本スキルが再帰的に呼ばれる経路ではこのステップは既に解決済みなので、自動的にスキップする
- 「シーケンス図なしで進める」 — 「機能別シーケンス図」セクションは省略、または自家製の簡略 sequenceDiagram 1〜2枚で対応。本スキルの Step 10 では「シーケンス図がない」前提で扱う
- 「既存シーケンス図はあるが古いので、本スキル内で再検証だけ行う」 — Step 10 で既存図を実コード突き合わせで再検証する（「既存図に書かれたデコード方式が実装ライブラリと食い違っていた」のような事実誤認を見逃さない）

シーケンス図が十分整備されている場合は、このステップはスキップして Step 2 へ。

### Step 2: 方針の3点質問

`AskUserQuestion` で以下を確認:

1. **更新方向**: 既存維持の最小更新 / 1段階詳細化 / 全面リライト
2. **想定読者**: 自分用 / 内部関係者・引き継ぎ先 / ポートフォリオ・対外公開
3. **スコープ**: README のみ / docs も整理 / submodule・untracked も整理

「対外公開・ポートフォリオ向け」が選ばれたら、Step 3 以降をフルに走らせる。「最小更新」なら検証のみで終える。

### Step 3: 素材集め（並列読み込み）

メイン文脈を汚さないために、以下を並列で Read:

- `CLAUDE.md`（プロジェクトメモリ）
- `docs/01-overview.md`（あれば）
- `docs/system-architecture.md`（あれば）
- 各サブシステムの README
- `package.json` / `pyproject.toml` / `requirements.txt`（依存関係）
- 既存シーケンス図（`docs/sequence-diagrams/` があれば README + 主要図）

3クエリを超えるコードベース探索が必要なら `Agent`（Explore）に委譲。

### Step 4: 構成案先行 → 合意

書き出す前に構成案をユーザーに提示。標準テンプレート:

```
1. Hero（中央寄せ・バッジ・1行サマリー）
2. 何を解決するか（課題 → 解決の表）
3. システム全体像（mermaid flowchart）
4. 想定ハードウェア構成（実装ベース、必要な場合のみ）
5. 実装ベースのライフサイクル俯瞰（既存シーケンス図あれば embed）
6. サブシステム詳細
7. 技術スタック（採用理由付き）
8. リポジトリ構成（網羅的に）
9. 機能別シーケンス図（既存資産があれば索引表）
10. 設計上のハイライト
11. クイックスタート
12. 運用ステータス
13. 関連ドキュメント
14. ライセンス・開発者
```

ユーザーが「いらない」と言ったセクションは削る。「これも欲しい」と言ったら追加する。**この段階で書き始めない**。

### Step 5: 初版書き起こし（粒度A）

サブシステムは1〜2行のサマリー、設計ハイライトは1行ずつ、で書く。**この時点では完璧を目指さない** — 後で必ず検証フェーズが入る前提で、構造だけ整える。

### Step 6: 実コード突き合わせ検証（最重要）★

Step 5 の初版で書いた**すべての具体的記述**を実コードと突き合わせる。検証チェックリスト:

| カテゴリ | 検証方法 |
|---|---|
| 数値（行数 / 間隔 / TTL / バージョン） | `wc -l` / `grep` / `Read` で実測 |
| 関数名 / ファイル名 | `Glob` / `Grep` で存在確認 |
| ライブラリ | `requirements.txt` / `package.json` を `cat` |
| 通信プロトコル / API | 実装ファイルの該当関数を `Read` |
| UI 要素（ボタン・スライダー・選択肢） | UI実装ファイル（`*_screen.py` / `*.html`）を `Read` |
| 使用順序・並び順 | UI コードの定義順を確認（統計集計時の正規値とは別物の可能性） |
| 既存ドキュメント記述の継承 | 元ドキュメントが間違っている可能性を常に疑う |

**よくある事故パターン**（実プロジェクトで実発生したものを類型化）:

- 既存ドキュメントに「外部メッセージング API（例: チャット連携）を使用」と書いてあったが、実装は別の送信手段（例: メール送信 API）だった。チャット連携は将来計画だった（**通信プロトコルは実コードで確認**）
- 設定ファイルのヘッダーコメントに「Raw / Master / Mart の3層構成」とあったが、実装の定数定義には Mart 層に相当するテーブルが存在せず、実態は2層だった（**コメントと実装の乖離を疑う**）
- アーキテクチャ図に「ライブラリ X でデコード」とあったが、依存定義ファイルに X が存在せず、実装は別方式（例: HID 型 USB スキャナ + 入力イベントハンドラ）だった（**依存定義ファイルで実在確認**）
- 「リアルタイム表示」を演出したくて、自動更新間隔が不明なまま推測で「30秒間隔」と書いた → 実装の定数は別の値（例: 5分）だった（**数値は推測しない、実測する**）
- 「0〜100 のスライダー」と書いたが、UI 実装は段階選択（例: アイコン5択）だった（**UI は UI 実装ファイルで確認**）
- README から参照する補足ドキュメント（例: `docs/<name>.md`）が untracked のまま → GitHub 上で 404（**リンク先が `git ls-files` にあるか確認**）
- 構成図に「サブディレクトリ X」と書いたが、`.gitignore` で除外され実は別 repo の clone だった（**`.gitignore` / `git submodule status` を最初に確認**）

事実誤認が見つかったら**ユーザーに即報告**してから修正する（黙って直さない）。

### Step 7: 1段階詳細化（粒度B、ユーザーが希望した場合）

`AskUserQuestion` で「どこを掘り下げるか」を multiSelect で確認:

- サブシステム詳細（役割 / 主要モジュール / 連携先 の3要素で展開）
- データフロー詳細（sequenceDiagram で主要フローを詳細化）
- 技術スタック詳細（採用理由列を追加）
- 設計ハイライト詳細（「何を / なぜ / どう実装」の3要素で深掘り）

選ばれたものだけ詳細化。**全部詳細化すると README が肥大化する** ので、ユーザーの選択を尊重する。

### Step 8: 想定ハードウェア構成（必要な場合のみ）

物理デバイスを伴うシステム（QRスキャナ・タッチパネル・ラベルプリンタ等）が関わるなら、ハードウェア構成セクションを追加:

- 配置図（mermaid flowchart で 拠点内 / クライアント / 利用者 のゾーン分け）
- 端末別要件表（OS / 役割 / 備考）
- ネットワーク要件 / 復旧手順への参照

実装で確認すべきこと:
- QR読み取り方式（カメラ + OpenCV/pyzbar か、HID 型キーボードエミュレーションか）
- タッチパネルの有無
- 配布形態（exe 単体配布 / Python 環境必須）

### Step 9: リポジトリ構成の網羅化

書く前に必ず実態確認:

```bash
git ls-files | awk -F'/' '{print $1"/"$2}' | sort -u    # 追跡対象の構造
git submodule status                                      # submodule
git status -s | grep "^??"                                # untracked
```

**重要な判断ポイント**:
- submodule あり → ツリー内に「★ git submodule（別リポジトリ参照）」と明示。`git clone --recursive` を案内
- 別 repo の clone がローカル配置されている（.gitignore で除外）→ submodule 化を提案
- 重要な untracked ファイル（マニュアル等）→ コミットするか提案
- README から参照するファイル → 全て tracked か確認（`git ls-files` で照合）
- 二重配置（例: `docs/pdf/foo.pdf` と `docs/foo.pdf`）→ どちらかに集約を提案

「網羅的に」と求められたら、ディレクトリツリーの2階層目までは原則網羅。3階層目は主要ファイルのみ。

### Step 10: 既存シーケンス図の活用（あれば）

`docs/sequence-diagrams/` 等が既にある場合、自家製の簡略 sequenceDiagram を README に書くより、既存の精度高い図を embed する方が良い。ただし:

1. **embed する前に既存図の事実確認を再度行う** — 「実コードベースで作成した」と書かれていても誤りが入っていることがある（過去に「既存図のデコード方式が実装ライブラリと食い違っていた」事例あり）
2. 全体俯瞰図は本文に embed、個別図はリンク表で案内
3. 「機能別シーケンス図」セクションを設け、表形式で索引化（# / フロー / 主要アクター / 技術ポイント / リンク）

`/mermaid-sequence-diagram` スキルの成果物を活用する形になる。

### Step 11: 完璧化（視覚的ブラッシュアップ + 最終検証）

#### 視覚的ブラッシュアップ
- **中央寄せ Hero**: `<div align="center">...</div>` でタイトル・1行サマリー・バッジを集約
- **shields.io バッジ**: status / 主要技術 / License など3〜5個。多すぎないように
- **目次**: GitHub は H2/H3 から自動生成するが、長い README は手動 ToC を入れると親切
- **区切り線**: セクション間に `---` を挿入してメリハリ
- **callout**: 重要事項は blockquote (`>`) で目立たせる
- **絵文字は使わない**（グローバルルール）
- **コードブロック**: シンタックス指定（mermaid / bash / javascript / python）

#### 最終検証
全 README の具体的記述を再度 grep で洗い、未修正箇所がないか確認:

```bash
# 旧記述（推測値・既存ドキュメント継承の罠）が残っていないか
grep -E "30秒|3層|pyzbar|opencv|スライダー" README.md
```

リンクの 404 確認: README で参照しているローカルファイルがすべて `git ls-files` の中に含まれるか確認。

### Step 12: コミット&プッシュ

論理的に分割:

- 初版〜詳細化: `docs: README をポートフォリオ・対外公開向けにリライト`
- 事実誤認修正: `docs: README の事実誤認を修正（X / Y / Z）`
- 構造変更（submodule / マニュアル群追加）: `chore: ...` `docs: ...`
- 最終完璧化: `docs: README を実コード突き合わせで完璧化`

master 直 push か PR か、ユーザーに確認（破壊的でない限りは master 直 push が多い）。

## 検証チェックリスト

push 前に以下を全てクリアすること:

- [ ] README の具体的数値はすべて実測値（`wc -l` / `grep` / コード内定数）
- [ ] 関数名・ファイル名は `Glob` / `Grep` で実在確認済み
- [ ] ライブラリ・バージョンは依存定義ファイルから取得
- [ ] 既存ドキュメント由来の記述は実コードで再検証済み（継承だけにしていない）
- [ ] submodule の有無を構成図に反映、`git clone --recursive` を案内
- [ ] README から参照する全ローカルファイルが `git ls-files` に含まれる
- [ ] mermaid 図のシンタックス確認（GitHub プレビューでレンダリング可能）
- [ ] バッジ・目次・区切り線・blockquote が適切に配置
- [ ] 絵文字を使っていない
- [ ] 推測値（「30秒」など）/ 既存ドキュメント継承（「Mart 3層」など）の罠が残っていない

## 注意点

- **「動くはず」「書かれているはず」で書かない** — 一次資料（実コード）で検証する。グローバル CLAUDE.md「一次資料・ファクトチェック原則」と整合
- **ユーザーから「本当に正しい？」と問われたら、即座にコード検証フェーズに戻る** — 自信を主張する前に grep で確認。過去にも初版 push 後にユーザー指摘でいくつもの事実誤認が見つかった例がある
- **段階的にコミット** — 「初版」→「事実誤認修正」→「詳細化」→「ハードウェア構成追加」→「網羅化」→「完璧化」のように、論理的に分けて履歴を残す。レビューしやすく、ロールバックもしやすい
- **untracked のリンク切れ** — README で参照するなら必ず tracked にする。マニュアル群が untracked のまま push すると GitHub 上で 404 が大量発生する
- **submodule 化の手順は慎重に** — 既存ローカル clone を残すために `git submodule add --force` を使うと既存 clone を尊重して登録できる。詳細は git docs を参照
- **数値の上書き精度** — 「約 8,650 行」のように丸めて書くのは OK だが、丸める前の実測値を必ず取る。後から「攻撃的に増やしたな」と思われない数字に
- **対外公開で人物プロフィールを書くときは本人合意を取る** — 学歴・肩書きのようなプロフィール項目は、本人合意なく勝手に書かない（過去に一度書いて削除になった例がある）

## 関連スキル・ルール

- **`/mermaid-sequence-diagram`** — 既存シーケンス図がない場合、先にこちらでシーケンス図を作ってから embed する流れが取れる
- **`/repo-health-check`** — Step 1 の起動時スキャンの代替として使える（プロジェクト構造・依存・git状態を一括取得）
- **`/doc-init`** — README 作成前に `CLAUDE.md` / `docs/01-overview.md` / ADR が揃っているか確認するために
- **`/design-actor-impact`** — サブシステムの「役割」を書くときに、アクター視点で構造化評価したい場合
- **グローバル CLAUDE.md「一次資料・ファクトチェック原則」** — 大原則1〜2の根拠
- **グローバル CLAUDE.md「コードベース検証時の視点」** — Step 6 の根拠
- **グローバル CLAUDE.md「進捗の可視化と小刻み進行」** — Step 12 のコミット分割の根拠

## 事故事例集（実プロジェクトで実発生したものを類型化）

後の自分が同じ失敗をしないように、誤りのパターンを類型として残す。固有のプロダクト名・実装名は伏せ、構造（何を継承・推測して、実態がどう違ったか）を保持する:

| 事例 | 何が起きたか | 学び |
|---|---|---|
| 外部メッセージング API 継承 | アーキテクチャ図の「チャット連携 API を使用」を継承 → 実装は別の送信手段（メール送信 API）。チャット連携は将来計画 | 通信プロトコルは実コードで確認 |
| データ層の層数 継承 | 設定ファイルコメントの「Raw / Master / Mart 3層」を継承 → 定数定義に Mart 層が不在 | コメントと実装の乖離を疑う |
| デコードライブラリ 継承 | アーキテクチャ図の「ライブラリ X でデコード」を継承 → 依存定義に不在、実態は別方式 | 依存定義ファイルで実在確認 |
| 更新間隔の推測 | 「リアルタイム表示」を演出するため独自推測で「30秒間隔」 → 実装は別の値（5分） | 数値は推測しない、実測する |
| UI 要素の推測 | 「0〜100 のスライダー」と書いたが UI は段階選択（アイコン5択） | UI は UI 実装ファイルで確認 |
| 行数過小 | 「約 2,200 行」→ 実測は別の値 | コード規模は `wc -l` で取る |
| submodule 見落とし | サブディレクトリを構成図に入れたが実は別 repo の clone | `.gitignore` / `git submodule status` を最初に確認 |
| 参照ファイル untracked | README から参照する補足ドキュメントが未コミット | リンク先が `git ls-files` にあるか確認 |
| 二重配置 | 同じ PDF が複数の docs パスに二重化 | 既存 docs の構造を最初にスキャン |
| 肩書き勝手書き | 学歴・専門性をプロフィールに本人合意なく記載 | プロフィール記述は本人合意を取る |
