# Exec Boundary Guard

操作実行前のリスク判定と発話フォーマットの手続き化。グローバル「自律実行ポリシー」の Green / Yellow / Red 区分を実行手順に落とし込んだもの。

## 起動条件

- ユーザー指示に「実行」「やって」「進めて」「マージ」「デプロイ」「削除」「リネーム」「移動」「インストール」「アップグレード」等の動作語が含まれるとき
- 明示呼び出し（「exec-boundary-guard で見て」等）

## 判定フロー

### Step 1: 操作の列挙
これから実行する予定の操作を列挙する。1指示に複数操作が含まれる場合、それぞれを別個に扱う。

### Step 2: 区分の判定

各操作を以下の表で分類する。グローバル CLAUDE.md「自律実行ポリシー」の定義と一致させる。

| 区分 | 例 |
|---|---|
| **Green** | コード読解、調査、lint / test / build、非破壊修正、テスト追加、文書整備、ローカルブランチ作成 |
| **Yellow** | 依存追加、マイグレーション作成、既存API挙動変更、UI変更、リネーム・ファイル移動、既存テスト期待値変更、ローカルコミット、**feature ブランチへの push** |
| **Red** | **main / master への push、force push**、本番デプロイ・本番DB操作、秘密情報の扱い、外部課金、データ削除、`reset --hard`、`rm -rf`、破壊的スキーマ変更、認証/権限変更、対外送信文の最終送信 |

### Step 3: 区分別の処理

#### Green
- **何もせず実行**
- ログ的にも「これを実行します」と明示しない（過剰確認の抑制）

#### Yellow
- 実行前に **1〜3行の発話** をしてから即実行する。**許可待ちはしない**
- 発話に必ず含める3要素:
  1. **何をするか**（理由を1行で）
  2. **影響範囲**（どのファイル / どの機能 / 誰の体験に影響するか）
  3. **主要リスク**（失敗時に何が壊れるか / ロールバック手段は何か）
- 発話例:
  ```
  〜の理由で <ファイル/機能> を変更します。影響は <誰/何> に及び、失敗時は <ロールバック手段> で戻せます。
  ```

#### Red
- 上記3要素を提示したうえで **「実行してよいですか」と明示的に確認待ちを宣言**
- ユーザー応答を待つ
- 応答前に実行しない

### Step 4: 連続操作・複合操作の扱い

- 同一指示内に複数操作 → 各々を分類
- Green は黙って実行、Yellow / Red のみ発話
- Yellow と Red が混在する場合は、Yellow を先に発話・実行し、Red は確認待ちで止まる
- 「Red を含むため止まります、Yellow までは進めました」のように現在地を明示する

## ユーザー指示の特例

- ユーザーが明示的に「黙ってやって」「説明不要」「Yellow も省いて」と言ったとき → Yellow の発話を省略してよい。**Red は省略しない**
- ユーザーが「全部止まって聞いて」と言ったとき → Yellow も確認待ちにする

## 既存スキルとの境界

- **deploy-check**: デプロイ前の build / lint / test 検証（事後確認）
- **exec-boundary-guard**: 操作前のリスク提示と区分判定（事前判定）
- **incident-response**: 本番障害時の Plan B / Plan A 並行対応（障害特化）

役割は補完的で重ならない。デプロイ前に exec-boundary-guard で Red 確認を取り、deploy-check で検証する流れになる。

## 重要原則

1. **Green は確認しない** — 過剰確認は本当に確認すべき場面のシグナルを薄める
2. **Yellow は発話して即実行** — 許可待ちは規律を弱める。事後フィードバックで矯正する
3. **Red は必ず止まる** — ユーザーが委任を明示していても、Red の対象操作は止まる
4. **区分の根拠はグローバル CLAUDE.md** — このスキルは判定の手続き化であり、区分自体の決定権は持たない。区分定義はグローバルを単一の真実とする
