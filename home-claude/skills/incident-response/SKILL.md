# Incident Response

本番障害対応の構造化ワークフロー。グローバル CLAUDE.md「問題フレーミングと障害対応の規律」を実行手順に落とし込んだもの。**業務影響の最小化** と **原因究明** を並行して進めるための足場。

## 起動条件

- 「本番が落ちた」「障害」「動かない」「inbound 失敗」「500」「ロールバック」「緊急」「データが見えない」「ユーザーから連絡が来た」等のトリガー語
- 明示呼び出し（「incident-response で対応」等）

## 出力フォーマット

障害対応セッションの最初に、以下の5ブロックを構造化して提示する。空欄は「不明」「未着手」と明示してよい。

### 1. 業務影響（1行）

「**誰が・何に・なぜアクセス（操作）できないか**」を**業務語彙で1行**。技術症状（「500エラー」「ログが出ない」）ではなく業務問題で書く。

例:
- ✓ 「Worker が今日のシフトを確認できず、勤務予定が分からない状態」
- ✗ 「`/api/shifts` が 500 を返している」

### 2. 即復旧候補（Plan B）

業務影響を最小化する手段を列挙する。**採用しない案も含めて書き出す**（思考フックとして）。

| 案 | 所要時間 | 副作用 | 採用可否 |
|---|---|---|---|
| 例: 直前リリースをロールバック | 5分 | 新機能Xが消える | ◯ |
| 例: 手動 migration で復旧 | 30秒 | コード状態とDB状態が一時不一致 | △ |
| 例: 該当機能をフィーチャーフラグでオフ | 2分 | 他機能への影響なし | ◯ |

### 3. 原因仮説（Plan A）

技術仮説をリスト化する。**観測装置の健康確認**と **schema drift / revision mismatch** を最初に置く（どちらも見落とすと長時間の暗中模索になりやすい）。

```
- [ ] 観測装置の健康確認
  - [ ] logger 設定（level、handler、出力先）
  - [ ] フィルタ・disable_existing_loggers の有無
  - [ ] 期待ログが期待先に出ているかの実機確認
- [ ] schema drift / revision mismatch の早期切り分け
  - [ ] /health/schema が match=true を返すか (実装済の場合)
  - [ ] flask db current で本番 head が期待値か
  - [ ] エラーログに psycopg.UndefinedColumn / UndefinedTable 等が出てないか
  - [ ] 直近の migration ファイルが production に適用されているか
- [ ] 引き継ぎメモの「確認済み」経路を実コードで再検証
  - [ ] CLAUDE.md / docs/notes/ の handoff 欄を併読
  - [ ] 「既知問題」「無関係」とラベルされた事項も今回の症状と三点照合
  - [ ] ラベルを引数として無効化し、症状・コード・実測で再確認
- [ ] 直前リリース差分の確認
- [ ] 外部依存サービスの状態確認
- [ ] その他の仮説（具体的に）...
```

### 4. Definition of Recovery

「**何が満たされれば復旧と呼ぶか**」を1〜3行。lint / test 通過は必要条件であって十分条件ではない（グローバル「完了判定」に従う）。実機・実環境の挙動確認を含める。

例: 「Worker が今日のシフトを画面で確認できる + 勤務予定の表示が正しい + 直近1時間の API エラーレートが平常値に戻っている」

### 5. 並行進行ルール

- **Plan B は採用しなくても列挙する**（思考フックとして）
- 原因究明（Plan A）に没頭して業務影響を放置しない
- **Plan A の進展が止まる、または業務影響が継続する場合は Plan B の採用を検討する**（時間の固定値ではなく、進捗と影響の判断ベース）
- 復旧操作（ロールバック、手動DB操作など）は Red 領域に該当する。`exec-boundary-guard` で受けて確認待ちにする

### 6. Red 操作即実行の判断補助

復旧操作は Red 領域だが、**業務影響が継続している場面では「事前確認 → 実行」のサイクルを最小化する**ことが復旧速度を決める。以下の条件で「即実行」を選択しやすくなる。

| 条件 | 判定 |
|---|---|
| 業務影響が現在進行中 (Worker / Admin が API 呼出失敗中) | ✅ 即実行寄り |
| Plan B の操作が冪等で副作用が小さい (例: migration 再適用、deploy rollback) | ✅ 即実行寄り |
| 操作前の DB snapshot / restore point が取れている | ✅ 即実行寄り |
| ユーザーが「コマンド実行はあなたが」と明示している | ✅ 即実行 |
| 操作が破壊的 (DROP / DELETE / TRUNCATE / reset --hard) | ❌ 事前確認必須 |
| 操作後の即時 verification 手段が無い | ❌ 事前確認必須 |
| 復旧後の影響範囲が読めない | ❌ 事前確認必須 |

**実行前 1〜3 行宣言** (Yellow 操作と同じ形式):
- 何をするか
- 影響範囲
- 失敗時のロールバック手段

例 (schema drift による障害):
> Red 操作の事前宣言: production DB に 2 つの additive migration (列追加 + テーブル新規作成) を適用。downgrade 可能、データ消失なし。

これを書いてから実行することで、ユーザーが事後にレビューしやすくなる。

## 実行手順

### Step 1: 第一報の構造化
障害報告を受けたら、まず上記5ブロックの**業務影響（1行）だけを最初に書く**。残りは並行収集してよい。

### Step 2: Plan B 列挙
復旧候補を3〜5案、所要時間と副作用付きで列挙。1案しか思いつかなくても「他にない」と確認する儀式が抜けの予防になる。

### Step 3: Plan A 着手（観測装置から）
観測装置の健康確認を最初に行う。logger 設定が壊れている前提で技術仮説を積み上げない。

### Step 4: Definition of Recovery 合意
「どこまでで復旧と呼ぶか」をユーザーと合意してから動く。事後の判断基準が曖昧だと「直ったかどうか」で再度議論になる。

### Step 5: 進行中の現在地報告
- Plan A / Plan B のどちらを進めているか
- 経過時間と進捗
- 業務影響の継続状況

### Step 6: 事後の振り返り（任意）
障害収束後、判断ログをセッション内に残し、必要に応じて feedback メモリ化する。

## 既存スキル/ルールとの関係

- **exec-boundary-guard**: 復旧操作（reset --hard、本番DB操作、force push）は Red 領域。確認待ちで受ける
- **deploy-check**: 復旧後の検証で併用。build / lint / test と git 状態の一括確認
- **グローバル CLAUDE.md「問題フレーミングと障害対応の規律」**: このスキルの根拠

## 重要原則

1. **業務語彙で語る** — 技術症状から始めない
2. **観測装置を最初に疑う** — コード推測の前に logger 設定
3. **Plan B を必ず列挙** — 採用しない案も書き出す（思考フック）
4. **時間の固定値ではなく判断条件で動く** — 「30分経ったら」ではなく「進展が止まる、または業務影響が継続する」
5. **復旧条件を先に合意する** — Definition of Recovery が曖昧だと再度議論になる
