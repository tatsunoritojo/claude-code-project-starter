# Design Actor Impact

設計変更案の**アクター視点での影響評価**。グローバル CLAUDE.md「コードベース検証時の視点」を構造化出力に落とし込んだもの。技術的判断を体験から逆算するクセを実行手順化する。

## 起動条件

- 「設計レビュー」「この変更どう？」「機能追加の影響」「リファクタしたいけど影響範囲は？」と指示
- ADR（Architecture Decision Record）起票前の前段ステップ
- 大きめのリファクタリング・機能追加の前
- 「工数抜きで考えると？」とユーザーから問われたとき

## 実行手順

### Step 1: 変更案の要約

ユーザーから提示された変更案を **1〜3行** に要約する。

- 何を変えるか（現状 → 変更後）
- 技術的な動機（性能、保守性、拡張性など）

### Step 2: アクター洗い出し

当該プロジェクトのアクターを特定する。優先順:

1. プロジェクト直下の `CLAUDE.md` を読む
2. `docs/01-overview.md` を読む
3. README、`src/` のディレクトリ命名（admin/, worker/ など）から推論
4. 不明な場合は **ユーザーに確認**（推論で進めない）

代表的なアクター例:
- **Admin** — 管理者・運営側
- **Worker** — 業務遂行者（講師、シフト勤務者など）
- **Owner** — 経営者・意思決定者
- **候補者 / 応募者** — 見込みユーザー
- **運用者 / オンコール** — 障害対応・運用担当
- **顧客 / エンドユーザー** — サービス受益者
- **外部連携先** — API 利用者・データ受け渡し相手

### Step 3: 影響マトリクス

各アクターについて以下を表で提示する:

| アクター | 何が変わる | 何が壊れる可能性 | 体験影響度 | 移行コスト |
|---|---|---|---|---|
| Admin | 設定画面の項目が3→5に増える | 既存の設定が読めなくなる可能性 | 中 | 既存設定の移行スクリプト要 |
| Worker | （変化なし） | （なし） | 低 | なし |
| Owner | レポート出力形式が変わる | 既存の月次レポート参照が割れる | 高 | 顧客への事前通知必要 |

**体験影響度** は **高 / 中 / 低** の3段階。判定基準:
- **高** — 既存の操作フロー・期待される画面・出力形式が変わる
- **中** — 設定や手順が増える / 減るが、コア体験は維持される
- **低** — 内部実装の変更で、アクター視点では気付かない

### Step 4: 工数軸の独立評価

- 工数を理由に体験を妥協していないか
- ユーザーから「**工数抜きで考えると？**」と問われたら、本来あるべき体験から逆算した推奨を出す
- 工数の話と体験の話は **最初から混ぜない**

### Step 5: 推奨

最終的な推奨を1行で提示する:

- **採用**: 体験影響度が許容範囲、移行コストが妥当
- **修正案あり**: 一部のアクターで影響度が高い → こう変えれば許容範囲になる
- **却下**: 体験を壊す。代替案を1つ提示

却下時は **代替案を1つ必ず提示**する。「ダメ」だけでは判断材料が減る。

### Step 6: ADR 化（任意）

設計判断を伴う変更で、影響評価が「採用」または「修正案あり」の場合、ADR を `docs/decisions/NNNN-<kebab-title>.md` に追加することを推奨する。

ADR テンプレ:
```markdown
## Status
Accepted（または Proposed）

## Context
<変更の背景・動機>

## Decision
<変更内容>

## Consequences
- アクター影響: <Step 3 の表を要約>
- 移行コスト: <Step 3 の表から>
- 採用しない選択肢: <なぜ採らなかったか>
```

## 既存スキル/ルールとの関係

- **doc-init**: プロジェクト初期化時の文書整備（このスキルとは別物）
- **グローバル CLAUDE.md「コードベース検証時の視点」**: このスキルの根拠
- **ADR 運用ルール（グローバル「プロジェクトドキュメント整備ルール」）**: Step 6 で参照

## 重要原則

1. **アクターから始める** — 技術的整合性から始めない
2. **影響度を高/中/低で言い切る** — 「ケースバイケース」で逃げない
3. **却下するなら代替案を出す** — 「ダメ」だけでは判断材料にならない
4. **工数と体験は最初から混ぜない** — 工数だけで議論すると体験軸が消える
5. **アクター定義が薄いプロジェクトはまずそこを直す** — このスキルの精度はアクター定義の精度に依存する。`<project>/CLAUDE.md` または `docs/01-overview.md` にアクター定義を追加することを推奨

## 注意

- アクター視点が薄い／不明確なプロジェクトでは、まずプロジェクト側の文書にアクター定義を追加する提案をする。曖昧な状態で影響評価を出しても精度が出ない
- 「全アクターに影響度低」と判定したときは、本当に全部に影響しないか **2回確認** する（楽観バイアスの抑制）
