# 0001. アーキテクチャ判断を ADR として記録する

日付: {{YYYY-MM-DD}}

## Status

Accepted

## Context

設計判断（フレームワーク選定・データモデル・運用方式など）は、後から「なぜそうしたのか」が失われやすい。コードには「何を」は残るが「なぜ」は残らない。判断の背景を残さないと、半年後の自分や引き継ぎ相手が、既に検討済みの選択肢を再検討したり、意図を読み違えて壊したりする。

## Decision

設計判断を伴う変更を加えるたびに、ADR（Architecture Decision Record）を `docs/decisions/NNNN-<kebab-title>.md` に1判断1ファイルで追記する。既存 ADR は原則変更しない（追記専用）。

## Consequences

- ポジティブ: 判断の「なぜ」が時系列で残る。腐敗しない（追記専用のため）。
- ポジティブ: AI セッションが過去の判断を参照でき、設計を壊す方向の提案を抑止できる。
- ネガティブ: 判断のたびに1ファイル書く手間がある。軽微な変更には起票しない運用で軽減する。
